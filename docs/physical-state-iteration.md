# Спецификация интеграции физического state и школьного корпуса

Дата: 2026-10-01. Репозиторий: Cube3-C3/Packages, ветка dev.
Проверенная исходная ревизия: 05cbbeca71553a5b5bcd66800b864a2b8c2b6396.
Статус: спецификация реализации; перечисленные новые возможности ещё не реализованы.
Документ конкретизирует приложенное ТЗ на основе текущего кода.

## 1. Цель и границы

Собрать цепочку:
Construction → экземпляры E* → геометрия Geo_style → interaction locus →
адресованные occurrences → P*/AST → пересчитанный state → проекция.

Школьный корпус расширяется после двух работающих примеров: C001 и block–surface.
Формула имеет статус integrated только при исполнении на конкретных occurrences
хотя бы одной конструкции. Наличие JSON-записи само по себе означает catalogued.

Сохраняются E*/C*/P*/Q*, AST aliases, рекурсивные P*, include[], overrides,
прямые links:{id,law,of}, slot-action и действующие паспорта.
LINK.json остаётся совместимым legacy/экспериментальным каталогом.
Matchin и PDD не входят в эту итерацию.
Новые E* описывают переиспользуемые физические типы, а не отдельные задачи или состояния.

- P014 берёт extension, затем переставляет конечную точку в L0+extension.

Эти наблюдения получены чтением кода. Исполнение и регрессионные проверки должны
быть выполнены первым коммитом реализации, до изменения поведения.

## 4. Контракт state и адресов

Предлагаемый минимальный результат:
{ construction_id, event_id, frame, instances, occurrences, interactions,
  dependencies, diagnostics }.

instances хранит type E*, стабильный instance path, transform в СИ,
разрешённые параметры и актуальную geometry.
occurrences хранит quantity_id + role + indexes + value + provenance.
provenance указывает источник: default/override/geometry/law/constraint,
law_id, relation_id, operand path и входные occurrences.
interactions хранит участников, locus на каждом, мировую точку/область,
Frame, нормаль/направление и event.
dependencies хранит входы и выходы применений законов.
diagnostics содержит адресованный блокер, а не молчаливый fallback.

Пример адреса (предложение, не существующий JSON API):
{
  quantity_id: "Q004",
  role: "elastic_force",
  indexes: [
    {kind:"membership", construction_id:"C001",
     element_id:"mass", relation_id:"link_hooke"},
    {kind:"event", event_id:"initial"}
  ],
  value: [0, 5, 0],
  frame_id: "E0",
  application_point: {element_id:"mass", reference:"center"}
}

Ключ строится из канонизированных полей, включая role и полный instance path,
с безопасным кодированием разделителей; перестановка indexes не меняет identity.
Повторные/противоречивые индексы отвергаются.
include namespace сохраняется без разбора element_id по первой точке.
Старый slotId отображается через отдельную таблицу slotId ↔ occurrence address.
Q* не размножаются для символов, состояний, разных тел и контактов.
event адресует снимок/переход; coordinate включает axis и Frame.

Вектор хранится математически в Frame; модуль и направление выводятся из value.
Точка приложения относится к взаимодействию, когда физически значима.
Нулевой вектор имеет нулевой модуль и неопределённое направление.
Отрицательная деформация меняет знак силы; нулевая длина оси даёт явную диагностику.

## 5. Геометрия и interaction occurrences

E.geometry задаёт способ построения, параметры берутся из occurrences экземпляра.
material_point допустим. Конечное тело получает rect/polygon/другую Shape,
пружина — физическую ось/Path и вычислимые места крепления.
Рисунок витков может быть отдельной проекцией этой оси.

Первое подмножество геометрии: Point/Vec, segment, rect, transform,
distance, unit, perp и контакт прямоугольника с конечным отрезком поверхности.
Проверяются попадание на отрезок, касание, зазор, проникновение и rotation.
Точность указывается в физических единицах; экранный масштаб её не меняет.
Обобщённые 3D-контакты и collision solver не требуются.

Locus хранит ссылку на shape/feature и локальный параметр либо именованный anchor,
а world point вычисляется из transform. Не хранить вручную выводимые world points.
Interaction kind: attachment/contact/field/constraint/topological.
Общий адресный маршрут сохраняется, алгоритм возникновения различается.
Электрическая цепь использует узлы/ветви, а не искусственный механический контакт.
E0 поставляет поле и Frame; gravity occurrence создаётся отдельно для каждого тела.

Relation identity стабильна при пересчёте одного взаимодействия,
но исчезнувший контакт не оставляет активную силу. Несколько contact features
одной пары участников должны иметь разные адреса.

## 6. Исполнение P*/AST и пересчёт

1. Раскрыть include[] существующим expandConstruction, сохранить исходные пути.
2. Разрешить defaults/overrides существующей семантикой resolveElementParams.
3. Построить occurrences и geometry в СИ.
4. Создать interactions из геометрии, declared attachments и полей.
5. Разрешить bindings на точные occurrences, включая вложенные P*.
6. Выбрать явный вычисляемый operand и выполнить зависимости.
7. Сформировать новый state и передать его проекции.

Роль/quantity — проверка совместимости, но не способ выбрать первое совпадение.
Вложенный operand адресуется полным AST/P path: например O3/P291/O2,
чтобы несколько применений одного P* не делили входы случайно.
Рекурсивный P291 delta получает явно адресованную пару length/rest-length
или пару event occurrences. Нельзя трактовать delta как тождество.

P005 хранится F=m*a; для state выбирается target acceleration и вычисляется F/m.
Первый executor поддерживает явный forward target, product/ratio/sum/neg/delta,
затем необходимые unary/power операции. Используется AST из FisUnits.instantiateLaw.
Зависимость не подменяется отдельным захардкоженным значением по law_id.
Геометрическая ориентация и сбор результирующей силы остаются runtime-задачами.

Ограниченный inverse solve разрешён для однозначных product/ratio/sum зависимостей.
EQ, нелинейные и циклические системы получают UNSUPPORTED_SOLVE/CYCLE,
пока конкретный сценарий не потребует соответствующего solver.
Деление на ноль, несовместимые размерности, нечисловое значение и неоднозначный
binding дают диагностику с construction/relation/operand address.

Начать с полного детерминированного пересчёта DAG.
Частичная invalidation оптимизируется только при измеренной необходимости.
Порядок links и UI layout не меняет результат.
В одном проходе derived extension не перемещает заданный груз обратно.
Для inverse режима явно выбирается управляющая величина и решаемая координата.
equilibrium — отдельная постановка, а не скрытая коррекция любого state.

## 7. Последовательность проверяемых коммитов

### A. Совместимость и адресация

Закрепить C001/C002/C003/C010, nested P*, exports и navigation hooks.
Исправить identity/value/thin-elements в mechanics.
Добавить тест повторного include C001 с двумя namespace и разными overrides.
Проверить collision ключей Q008 natural_length/extension, event и Frame.
Готовность: адресованные значения доступны без DOM, старые C* загружаются.

### B. Сквозной C001

Геометрия anchor/end → current_length → extension → P014 →
вектор силы на mass → gravity → net force → P005(target a) → state.
При y вверх: Fg=[0,-mg,0], Fspring направлена к anchor при растяжении.

Численная приёмка для точечных anchors исходного C001:
anchor=(0.5,0.9,0), mass=(0.5,0.65,0), L0=0.2, k=100, m=0.5, g=9.8.
L=0.25, extension=0.05, Fspring=(0,5,0), Fg=(0,-4.9,0),
Fnet=(0,0.1,0), a=(0,0.2,0), с допуском floating point.
При k=200: Fspring_y=10, a_y=10.2; заданное положение остаётся тем же.
При mass_y=0.7 и k=100: extension≈0, a_y=-9.8.
Контуры конечных объектов используют геометрические anchors и свою отдельную
численную приёмку; центр и точка крепления не отождествляются автоматически.

Проекция использует этот же state. Изменение масштаба не меняет численные значения.
Произвольные имена экземпляров и перестановка links дают тот же результат.
Отдельно проверить обратный режим force→extension→position и равновесие,
если они сохраняются как публичные действия.

### C. Контакт block–surface

Те же E002/E003 с geometry overrides создают rect и поверхность.
Runtime вычисляет контакт, feature address, нормаль и силы.
Первый режим: покоящийся брусок на неподвижной горизонтальной поверхности,
без трения и без универсального collision solver.
При m=0.5,g=9.8 реакция вверх 4.9 Н, net force≈0.
При зазоре реакция=0; при выходе за конечный отрезок контакта нет.
Проникновение возвращает диагностику либо применяется явно заданное ограничение.
На наклонной нормаль выводится из поверхности; отдельно проверяется проекция mg.
Нельзя автоматически приравнивать N=mg для произвольной динамической сцены.

### D. Переиспользование и время

C002 суммирует только силы, приложенные к mass.
C003 требует различить конец каждой пружины и промежуточное соединение.
Если безмассовый узел требует equilibrium solver — записать этот блокер;
не суммировать силы всех пружин на груз ради прохождения теста.
C010 и повторный include проверяют изоляцию state.

Затем свободное движение и gravity: event(t) → event(t+dt),
явно выбранный интегратор, единицы dt, проверка аналитического решения/сходимости.
Столкновение хранит before/after occurrences; его solver вводится отдельным
сценарием с явно ограниченными условиями (например одномерное упругое).
Не добавлять time-step до прохождения B/C.

### E. Школьный корпус

Для каждой порции одновременно добавить P/Q/usages/units при необходимости,
construction bindings и численный тест. Существующие ID сохранять;
новые выдавать после проверки полного реестра, включая denotations.
Сначала инвентаризация имеющихся законов, затем список отсутствующих.

| Раздел/сценарий | Проверяемая способность |
|---|---|
| Кинематика: свободная точка | event, координата, скорость, время |
| Тяжесть и гравитация | E0/поле, разные тела, расстояние и направления |
| Горизонтальная/наклонная поверхность | контакт, нормаль, реакция, затем трение |
| Одна/несколько пружин | attachments, повторный P014, агрегация сил |
| Маятник | ограничение длины, tension и адресованный pivot |
| Столкновение | before/after, импульс, условия solver |
| Жидкость/погружение | погружённый объём из геометрии, P013 |
| Теплота/газ | state/event, температура, энергия, объём; EQ отдельно |
| Электрическая цепь | топологические nodes/branches, ток/напряжение |
| Электрическое/магнитное поле | бесконтактный locus, векторы, углы/произведения |
| Колебания/волны/оптика | фаза, пути, интерфейсы сред, ограничения EQ |
| Атомная/ядерная физика | энергетические переходы и константы |

Максимальная широта — цель, не обещание полноты без матрицы покрытия.
Статусы: catalogued, bound, executable, integrated, blocked.
blocked обязан содержать construction и конкретную отсутствующую операцию.
P036 уже требует семантической проверки: описание Ek=A+hν не соответствует
обычной связи энергии фотона, работы выхода и кинетической энергии.
P220 square(radius_vector) требует явного различения нормы и покомпонентного
квадрата. Размерности сами по себе такие ошибки не обнаруживают.

## 8. Проверки и способ работы

Перед кодом зафиксировать parent SHA, инструкции репозитория и baseline.
В проверенном дереве dev нет AGENTS.md, package.json и каталога tests:
headless harness следует добавить минимально, без внешних зависимостей,
используя Node built-ins и загрузку browser IIFE с явным global/window адаптером.

Обязательные группы:
- ссылки Q/P/E/C, aliases, denotations, units/usages; duplicate IDs; циклы include/P;
- размерности AST, delta/sum, безразмерные аргументы sin/cos, векторные операции;
- occurrence identity, namespace, несколько контактов и event snapshots;
- численные B/C/D, порядок links, независимость от viewport;
- отсутствующие/неоднозначные bindings, нулевая масса/ось, unsupported EQ;
- паспорта, navigation slot-actions, graph quantity/units и точки приложения векторов.

Для формул EQ проверять размерности обеих сторон и residual известного решения.
Не выдавать residual check за наличие общего solver.
Для контактов и интегратора документировать условия применимости и допуски.

Работать локальными файлами с запуском harness; затем отправлять атомарный
коммит в dev через GitHub Git Data API (base tree → tree → commit → ref).
Перед ref update повторно проверить branch head; force=false.
При новом внешнем коммите пересобрать изменения на новом parent и повторить проверки.
Не писать пачку отдельных contents-коммитов для одной взаимозависимой порции.

Допустимая параллельная работа после контракта B: геометрия, executor,
корпус и тесты — с раздельным владением файлами.
State-контракт и общий интеграционный тест имеют одного ответственного.
Данные корпуса не опережают исполнение своих сценариев.
Каждый коммит содержит работающую проверяемую точку и краткий результат тестов.

Итог реализации: state + geometry + interactions + P execution + projection,
конструкции разных механизмов, матрица расширенного корпуса, выполненные тесты
и короткий перечень воспроизводимых блокеров. Этот документ фиксирует порядок
работы; сам по себе он не меняет вычислительные возможности пакета.
